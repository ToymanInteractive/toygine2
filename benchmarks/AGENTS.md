# AI AGENTS rules for Benchmarks

Rules for benchmarks in this repository. Bold section names refer to the root [`AGENTS.md`](../AGENTS.md) unless the section appears in this file.

## Benchmarks

Building, running, and gating. What a body measures follows **Benchmark Shape** below, case names **Naming Benchmarks**.

* **What a benchmark answers:** Measures a system against its declared per-frame budget (see Budgets and profiling); not a correctness test, never gates a merge. CI builds them on desktop jobs but runs `<library>-benchmarks-run` only on the Nintendo GBA and Sega MD jobs, under mGBA and BlastEm, for a Bencher report; desktop numbers are local, and a result is a number a human reads.
* **Measured under optimization:** Numbers come from a `<platform>-benchmarks` preset (`macos`, `linux`, `md`, `gba`): the RelWithDebInfo configuration with assertions compiled out and only the engine and the benchmarks configured. `cmake/ConfigureCompiler.cmake` adds `-O3` after the configuration's `-O2`, so GCC and Clang compile the measured code at `-O3`. Desktop runs on the host with the host compiler; Nintendo GBA and Sega MD build in the CI toolchain images (`ghcr.io/toymaninteractive/toygine2.gba.toolchain`, `ghcr.io/toymaninteractive/toygine2.md.toolchain`). The debug presets pass no `-O`, so an inline header-only type is measured uninlined and unvectorized, and the ratio can come out wrong in either direction. Debug builds check that a benchmark runs, never what it costs.
* **Assertions compiled out:** RelWithDebInfo keeps `TOYGINE_DEBUG`, so every `assert_message` stays inside the timed loop, and checks that revalidate the whole string (`toy::string_utils::utf8Len()`, `toy::string_utils::utf16Len()`) cost two to three times the operation itself. The hidden `no-assertions` preset adds `-DTOYGINE_ASSERTIONS_DISABLE` to `CXXFLAGS` in the configure environment, which CMake joins to the toolchain flags. `-DCMAKE_CXX_FLAGS` is no substitute: it replaces the console toolchain flags (`-march=armv4t -mthumb` on GBA), and a cached value ignores a later `CXXFLAGS`, so the preset keeps a build directory of its own.
* **Library and layout:** nanobench on desktop, the built-in runner on consoles, one file per public type at `benchmarks/<module>/<name>.benchmark.cpp`, gated by `TOYGINE_BUILD_BENCHMARKS` so engine consumers never pull the dependency in (see Build-only dependencies).
* **Where numbers come from:** desktop times with nanobench; Nintendo GBA and Sega MD build the runner in `benchmarks/runner/` over a hardware timer (GBA Timer 2 and 3, MD frame count and V counter); every other console skips the tree in `benchmarks/CMakeLists.txt`. A console number comes from the console, or from an emulator that derives that timer from emulated CPU cycles, which holds only for a CPU without a cache, the ARM7TDMI and the 68000 here.
* **One binary:** every `*.benchmark.cpp` links into `<library>-benchmarks` beside the runner in `benchmarks/runner/`. A `file(GLOB_RECURSE ... CONFIGURE_DEPENDS)` in `benchmarks/CMakeLists.txt` picks up a new file, so adding one costs no CMake; `BENCHMARK_CASE` registers the cases inside it. `<library>-benchmarks-run` builds and runs it: natively on desktop, under `mgba-headless` on GBA and `blastem` on MD if found.
* **Selecting what runs:** a pattern runs every benchmark whose name carries it as a substring, and no pattern runs all. `--list` first prints each name with the file and line declaring it instead of running; patterns after it narrow that listing. An unknown leading `--` option, or any pattern that matches no name on its own, ends the run with an error and exit code 1. Console runners take no arguments and run all.
* **Machine-readable report:** `--csv` prints one `#csv`-prefixed line per table row beside the tables — `case,row,unit,ps_per_tick,epochs` once, then an `iters,ticks` pair per timed epoch, with the whole epoch in `ticks` and one picosecond per tick on a desktop. Naming a row once rather than once per epoch keeps the log an order of magnitude shorter. `--no-table` takes the stream away from nanobench, so a run gives the data alone. Medians, spreads and the Bencher report come from `tools/builder/bmf_from_csv.py` on the host. A console ROM prints these lines alone, with `ps_per_tick` set to its hardware tick and seven epochs, the most a 256-byte mGBA log message holds.
* **One entry point:** every benchmark translation unit includes `benchmarks/runner/toy_benchmark.hpp`, never nanobench directly — the registry lives there, and a file reaching past it registers nothing. Bodies use `toy::benchmark::Bench`: nanobench on desktop, the built-in runner on consoles.
* **Deterministic order:** the registry sorts by name, so tables print in name order whatever order the linker gave the objects; no benchmark depends on running before or after another. A repeated name ends the run before the first table: the name both titles a table and selects it.
* **Console reports:** a GBA or MD ROM writes the report to the emulator debug channel (mGBA log, MD VDP debug port) and cartridge SRAM, then turns the backdrop green on `# done`, red on a repeated name or on a row printed as a comment, which ends the report in `# failed rows: N` instead. Reset only after the color changes; on a flash cart read the `.sav` or `.srm` file. `tools/builder/bmf_from_csv.py` reads that log as on desktop; two runs of one ROM must match line for line, and CI rejects a log without `# done`.

## Benchmark Shape

* **The runner owns the table:** title, ratio column and epoch length come from the runner (`benchmarks/runner/platforms/desktop.cpp` on desktop, `toy::benchmark::Clock` on consoles), which is what keeps two tables comparable; a body sets the unit and calls `run()` once per row.
* **One operation per case:** rows compare implementations of one operation. Two operations make the ratio column meaningless, so they are two cases.
* **A row needs something to measure against:** an engine type against its standard-library equivalent (`std::string_view` beside `toy::StringView`), or against the implementation it replaces — a lone number states neither a budget nor a regression. The engine row goes first; the standard-library row and the data only it reads close the case under `#if defined(TOYGINE_BENCHMARKS_STD_REFERENCE)`, and a case whose engine row reads `std` data goes under it whole. Only desktop builds define it, since standard-library comparisons are read locally; a console report carries the engine row alone, and its Bencher history is the regression check.
* **Keep the compiler honest:** every measured result goes through `toy::benchmark::doNotOptimizeAway`, and a foldable input reaches the body through an opaque barrier. A benchmark over a folded constant still prints a number, which is worse than printing none.
* **Arrange outside the loop:** whatever is not the subject of the measurement is built before `run()`, so the timed callable holds the operation alone.
* **Data the cache can hold:** state the size a case works over and why. A working set that spills out of cache measures the memory system, not what the name promises.

## Naming Benchmarks

* `BENCHMARK_CASE` names follow `<namespace>/<class>/<operation>`, the shape `TEST_CASE` uses (see Naming Tests in [`tests/AGENTS.md`](../tests/AGENTS.md)): `toy::` stripped from the namespace, every slash-separated segment `lowercase_snake_case`.
* The name titles the table, so it reads alone in a report — `core/string_view/find`, never `find` or `benchmark_1`.
* Row names are the implementations compared, spelled the way the code spells them: `toy::StringView`, `std::string_view`.
