# Терминальный тетрис как семпл движка

Дата: 2026-10-21
Расположение: `samples/tetris/`
Платформы: Linux Desktop, macOS Desktop

## Зачем

В репозитории один семпл — `samples/console`, который печатает hello world и завершается. Он показывает ровно одну вещь: как унаследоваться от `toy::application::ConsoleApplication` и развернуть `IMPLEMENT_CONSOLE_APP`. Для движка, который задуман под игры, этого мало.

Тетрис нужен как второй семпл — игра, которую можно запустить и поиграть. Она показывает, как на движке строится настоящий цикл: ввод, фиксированный шаг симуляции, отрисовка кадра, состояние, завершение игры.

Сейчас в движке нет ни ввода, ни тайминга, ни консольного видео — из модулей существуют только `core` (строки, ассерты, типы лога), `application` (`Version`, `BaseApplication`, `ConsoleApplication`) и `video` (один `Color32`). Поэтому семпл строится прямо на POSIX API. Это осознанное решение владельца: позже, когда движок обзаведётся собственным API для ввода и консольного вывода, семпл будет портирован на него. Значит, сегодня всё, что можно отделить от POSIX, должно быть отделено — иначе портирование превратится в переписывание.

## Цели

- Играбельный тетрис по полному Tetris Guideline: SRS с wall kicks, 7-bag, hold, ghost, hard и soft drop, lock delay с move reset, T-spin (full и mini), back-to-back, perfect clear, combo, полная таблица скоринга.
- Разделение на два слоя: чистая игровая логика без единого syscall и платформенная обвязка на POSIX. Первый слой переносится на API движка без переписывания.
- Стабильная картинка: без мерцания, без разрывов, без 100 % загрузки процессора.
- Терминал восстанавливается при штатном выходе, по Ctrl-C, по сигналу завершения и при провале `assert_message`.
- Семпл собирается и запускается одной командой на Linux и macOS Desktop.

## Не-цели

- Никаких изменений в движке: ни новых модулей, ни правок `ConsoleApplication`, ни новых заголовков в `include/`.
- Windows: `console_application_posix.cpp` компилируется только на Linux и macOS, `IMPLEMENT_CONSOLE_APP` на Windows отсутствует, а вместо `termios` понадобился бы `SetConsoleMode`. Отдельная задача.
- Игровые консоли (GBA, NDS, Switch и прочие): у них свои `main()` и свой вывод, никакого POSIX.
- Звук.
- Обработчики `SIGSEGV` и `SIGABRT`, спасающие терминал при настоящем падении. Восстановление покрывает штатный выход, сигналы завершения и провал `assert_message`; на большее семпл не замахивается.
- Таблица рекордов, сохранение, запись и воспроизведение реплея, seed из аргументов командной строки.
- Поворот на 180°: в стандартный набор управления Guideline не входит.
- Тесты в `tests/`: семплы живут вне модульной раскладки, а тестовый раннер собирает исходники из `tests/<module>/`. Логика пишется чистыми функциями именно для того, чтобы тесты можно было добавить позже, когда правила переедут в движок.
- Doxygen-блоки: `samples/` входит в `EXCLUDE` в `docs/Doxyfile.in`, поэтому документирование семпла не требуется. Комментарий — обычный `//` в одну строку, по правилам **Code Quality** из `AGENTS.md`.

## Анти-цели

Что считается провалом, даже если игра запускается и в неё можно играть:

- Мерцающий или рвущийся экран. Перерисовка кадра обязана быть дифференциальной и уходить в терминал за минимум системных вызовов.
- Игровая логика, которая знает про `termios`, `read`, `write`, `clock_gettime` или ANSI-эскейпы. Тогда портирование на API движка равносильно переписыванию, и весь смысл семпла потерян.
- Занятость процессора под 100 % в ожидании ввода.
- Сломанный терминал после Ctrl-C, штатного выхода или провала `assert_message`: raw-режим и alternate screen остаются, шелл не пригоден к работе.
- Новый API, добавленный в движок «только для тетриса».

## Ограничения

Из репозитория, нарушать нельзя:

- C++23, исключения и RTTI выключены, предупреждения — ошибки. Значит, ни `throw`, ни `dynamic_cast`, ни `typeid`; ошибки возвращаются кодом и печатаются через `writeErrorLine`.
- Никакого динамического выделения памяти: все буферы фиксированной ёмкости, статические или на стеке.
- Каждый исходный файл начинается блоком из `tools/builder/license/header_c_like.txt`, каждый `CMakeLists.txt` — блоком из `header_script.txt`; проверяет `tools/builder/check_source_headers.sh`.
- `.clang-format` — единственный авторитет по разметке: 2 пробела, 120 колонок, прикреплённые скобки.
- Имена: `PascalCase` для типов, `camelCase` для функций и переменных, `snake_case` для пространств имён и файлов, константы уровня файла — `c_` плюс `camelCase`, приватные члены — с `_` в начале.
- Логирование — макросы `LOG_*`, но в движке пока есть только типы лога (`Level`, `Metadata`, `Record`, `ISink`) и ни одной реализации. Значит, диагностика семпла идёт через `ConsoleApplication::writeErrorLine`, а не через `printf`.

Из POSIX-реальности:

- macOS Terminal.app не поддерживает truecolor, только 256 цветов. Поэтому палитра — xterm-256 (`ESC[38;5;Nm`), не `38;2;r;g;b`.
- В raw-режиме флаг `ISIG` выключен, так что Ctrl-C не порождает `SIGINT`, а приходит байтом `0x03`. Его нужно обрабатывать как команду выхода.
- Голый `ESC` неотличим от начала CSI-последовательности без таймера. Поэтому `ESC` не назначается ни на что, выход — `Q` или Ctrl-C.
- Терминал сообщает только о нажатии: байт приходит, когда клавиша нажата и когда автоповтор терминала её повторяет. События отпускания нет — ни при удержании, ни при отпускании. Поведение «удержанной» клавиши приходится строить на таймерах приложения, а не на отпускании.
- Символы блока (`█`, `░`, `╔`) — трёхбайтовый UTF-8. Буфер экрана хранит codepoint'ы, кодирует их уже рендерер.

## Что решено владельцем

- Правила — полный Tetris Guideline, включая T-spin, back-to-back и perfect clear.
- Раскладка — панель вокруг поля: hold слева, очередь из пяти фигур и счётчики справа, подсказка клавиш снизу.
- Удержание стрелки вбок — DAS около 100 мс, затем ARR мгновенный: фигура уезжает до стены за один шаг.
- Объём — только игра: старт, партия, пауза, game over с итогами, рестарт по клавише.
- Семпл регистрирует обработчик `toy::assertion`, который восстанавливает терминал и печатает провал перед `Action::Break`. Обработчики сигналов падения не добавляются.

## Мои решения

Всё ниже — мои вызовы, владелец их явно не подтверждал.

- Семпл строится на POSIX, движок не трогает; из движка берётся только `ConsoleApplication` (точка входа, `version()`, диагностика), `StringView`/`FixedString`, `assert_message` и `toy::assertion` для обработчика провала проверки. `Color32` не используется: ячейка кадра хранит индекс xterm-256, а не цвет.
- Новый каталог `samples/tetris/`, отдельный исполняемый таргет, подключается только на Linux Desktop и macOS Desktop.
- Поле 10 × 20 видимых клеток.
- Seed берётся из наносекунд `clock_gettime(CLOCK_MONOTONIC)`, смешанных с `pid()` через splitmix64. `std::random_device` не используется намеренно: он может бросить исключение, а исключения в сборке выключены. Seed хранится в `GameState`, наружу не выводится и аргументом не передаётся; рестарт по `R` берёт новый seed.
- Цвет — 256-цветная палитра xterm, по одному цвету на фигуру.
- Ввод ждётся через `poll()` на stdin с таймаутом до границы кадра. `O_NONBLOCK` не ставится: флаг повис бы на fd, унаследованном от шелла, а `poll` заодно убирает и отдельный `nanosleep`, и задержку ввода до 16 мс.
- Фиксированный шаг симуляции 1/120 с, аккумулятор и все интервалы в микросекундах, рендер не чаще 60 Гц.
- Интерполяции презентации нет: сетка дискретна, промежуточных состояний у клетки не существует. Это осознанное отступление от **Game Engine Development Best Practices**.
- POSIX feature-макросы (`_DEFAULT_SOURCE`, `_GNU_SOURCE` на glibc, `_DARWIN_C_SOURCE` на macOS) объявляются через `target_compile_definitions` только для таргета семпла. `CMAKE_CXX_EXTENSIONS OFF` даёт `__STRICT_ANSI__`, без этих макросов glibc прячет `cfmakeraw`, `SIGWINCH` и `TIOCGWINSZ`. Движка это не касается.

### Чистая игровая логика

Пространство имён `tetris`. Ни ввода, ни времени, ни вывода: состояние продвигается явными вызовами, прошедшее время передаётся аргументом в микросекундах.

```cpp
enum class PieceKind : uint8_t { i, j, l, o, s, t, z };
enum class Rotation : uint8_t { spawn, clockwise, double_, counterClockwise };
enum class Phase : uint8_t { playing, paused, gameOver };

struct GameState;                 // открытый агрегат: поле, фигура, очередь, hold, счёт, флаги, фаза

void  startGame(GameState & state, uint64_t seed) noexcept;
void  advance(GameState & state, uint32_t elapsedMicroseconds) noexcept;
bool  tryShift(GameState & state, int32_t dx) noexcept;
bool  tryRotate(GameState & state, Rotation direction) noexcept;
void  softDrop(GameState & state) noexcept;
void  hardDrop(GameState & state) noexcept;
void  swapHold(GameState & state) noexcept;
void  togglePause(GameState & state) noexcept;

uint32_t gravityInterval(const GameState & state) noexcept;      // микросекунды на ряд при текущем уровне
uint32_t softDropInterval(const GameState & state) noexcept;     // то же для удержанной стрелки вниз
```

`advance` — единственная функция, продвигающая время; она принимает прошедшие микросекунды и ничего не запрашивает наружу. Внутри неё живут только гравитация и lock delay. Повтор при удержанной клавише (DAS, ARR, soft drop) здесь не живёт: им владеет платформенный слой, который по своим таймерам дёргает `tryShift` и `softDrop`. `softDropInterval` — единственный способ, которым тайминг утекает наружу.

`GameState` — открытый агрегат, презентация читает его поля напрямую. Так сделано намеренно: когда семпл будут переносить на API движка, переноситься будет ровно эта структура, и скрыть её за аксессорами значит усложнить перенос. Прямое чтение допустимо только на построение кадра; менять состояние имеет право лишь перечисленный выше набор функций.

Презентации из состояния нужны: закреплённые клетки поля, активная фигура с видом, поворотом и позицией, позиция ghost, очередь из пяти следующих, содержимое hold и флаг `holdUsed`, `score`, `level`, `lines`, флаги `combo` и `backToBack`, `phase` и причина завершения игры (block out или lock out). Всё это — поля `GameState`, а не вычисляемые значения; ghost пересчитывается и запоминается при каждом успешном перемещении.

#### Поле

10 столбцов × 24 ряда внутренне; ряды 0–3 — скрытый буфер над видимым полем, ряды 4–23 — видимые 20. Хранится как `std::array<Cell, 240>` в `GameState`, где `Cell` — либо пусто, либо `PieceKind` закреплённой фигуры. Никаких указателей, никакого кучевого хранения.

Фигура появляется так: ограничивающий квадрат ставится верхним рядом в 2, левым столбцом в 3 для I, J, L, S, T, Z и в 4 для O, затем делается один немедленный шаг вниз, если клетка свободна (поведение Guideline). `Block Out` — клетки появления уже заняты. `Lock Out` — фигура закрепилась целиком в скрытых рядах. Оба завершают игру и запоминаются как причина в `GameState`.

#### Фигуры и SRS

Форма задаётся только для состояния `spawn`, остальные три получаются поворотом по часовой внутри ограничивающего квадрата: 4 × 4 для I, 3 × 3 для J/L/S/T/Z, 2 × 2 для O. Клетки состояния `spawn` в координатах квадрата `(столбец, ряд)`, ряд 0 — верхний:

| Фигура | Клетки |
| --- | --- |
| I | (0,1) (1,1) (2,1) (3,1) |
| O | (0,0) (1,0) (0,1) (1,1) |
| T | (1,0) (0,1) (1,1) (2,1) |
| S | (1,0) (2,0) (0,1) (1,1) |
| Z | (0,0) (1,0) (1,1) (2,1) |
| J | (0,0) (0,1) (1,1) (2,1) |
| L | (2,0) (0,1) (1,1) (2,1) |

Поворот по часовой стрелке внутри квадрата размера `n`: `(x, y)` переходит в `(n - 1 - y, x)`.

Все семь форм в состоянии `spawn` умещаются в 4 клетки в ширину и 2 в высоту — это определяет размер слота предпросмотра.

#### Wall kicks

Пять проб на каждый переход, координаты `(x, y)`, где `x` вправо, `y` вверх. Пробуются по порядку, берётся первая, при которой фигура ни с чем не пересекается и не выходит за поле.

Для J, L, S, T, Z:

| Переход | Проба 1 | Проба 2 | Проба 3 | Проба 4 | Проба 5 |
| --- | --- | --- | --- | --- | --- |
| spawn → clockwise | (0,0) | (-1,0) | (-1,+1) | (0,-2) | (-1,-2) |
| clockwise → spawn | (0,0) | (+1,0) | (+1,-1) | (0,+2) | (+1,+2) |
| clockwise → double | (0,0) | (+1,0) | (+1,-1) | (0,+2) | (+1,+2) |
| double → clockwise | (0,0) | (-1,0) | (-1,+1) | (0,-2) | (-1,-2) |
| double → counterClockwise | (0,0) | (+1,0) | (+1,+1) | (0,-2) | (+1,-2) |
| counterClockwise → double | (0,0) | (-1,0) | (-1,-1) | (0,+2) | (-1,+2) |
| counterClockwise → spawn | (0,0) | (-1,0) | (-1,-1) | (0,+2) | (-1,+2) |
| spawn → counterClockwise | (0,0) | (+1,0) | (+1,+1) | (0,-2) | (+1,-2) |

Для I:

| Переход | Проба 1 | Проба 2 | Проба 3 | Проба 4 | Проба 5 |
| --- | --- | --- | --- | --- | --- |
| spawn → clockwise | (0,0) | (-2,0) | (+1,0) | (-2,-1) | (+1,+2) |
| clockwise → spawn | (0,0) | (+2,0) | (-1,0) | (+2,+1) | (-1,-2) |
| clockwise → double | (0,0) | (-1,0) | (+2,0) | (-1,+2) | (+2,-1) |
| double → clockwise | (0,0) | (+1,0) | (-2,0) | (+1,-2) | (-2,+1) |
| double → counterClockwise | (0,0) | (+2,0) | (-1,0) | (+2,+1) | (-1,-2) |
| counterClockwise → double | (0,0) | (-2,0) | (+1,0) | (-2,-1) | (+1,+2) |
| counterClockwise → spawn | (0,0) | (+1,0) | (-2,0) | (+1,-2) | (-2,+1) |
| spawn → counterClockwise | (0,0) | (-1,0) | (+2,0) | (-1,+2) | (+2,-1) |

O не сдвигается никогда. Номер сработавшей пробы запоминается в состоянии: он нужен для T-spin.

Внутренне координаты поля идут сверху вниз, поэтому знак `y` из таблиц инвертируется при применении.

#### Очередь и hold

Очередь — 7-bag: все семь фигур перемешиваются и раздаются по порядку, по исчерпании перемешивается новый мешок. Видно пять следующих. Перемешивание — Fisher-Yates на splitmix64 от seed, хранящегося в `GameState`; `<random>` в логике не используется, только `uint64_t` арифметика, чтобы результат был одинаков на любом компиляторе.

Hold — одна ячейка и флаг `holdUsed`. Обмен запрещён, пока флаг поднят; флаг сбрасывается, когда фигура закрепляется. Фигура, пришедшая из hold, всегда входит в состоянии `spawn`.

#### Ghost

Низшая позиция, в которую активная фигура может упасть без столкновения. Пересчитывается после каждого успешного сдвига, поворота и шага гравитации. Рисуется в видимых рядах, в скрытых — нет.

#### Lock delay

500 мс. Таймер сбрасывается на ноль при каждом успешном сдвиге или повороте, но не больше 15 раз подряд. Счётчик сбросов обнуляется, когда фигура оказывается на новом для себя нижнем ряду — именно это не даёт «бесконечному вращению» на краю уступа. Таймер идёт, только когда фигура стоит на опоре.

#### Гравитация

Guideline: секунд на ряд — `(0.8 - (level - 1) * 0.007) ^ (level - 1)`. Уровень 1 — один ряд в секунду, уровень 15 — около 150 рядов в секунду, то есть фактически 20G. Уровень растёт на 1 за каждые 10 очищенных рядов и упирается в 15. Внутри интервал хранится в микросекундах.

Soft drop — интервал гравитации, делённый на 20, с полом в 1000 мкс: начиная примерно с 13 уровня деление даёт меньше миллисекунды, и без пола фигурой управлял бы уже платформенный слой, а не правило. `softDropInterval` возвращает значение уже с полом. Очко начисляется за каждый пройденный ряд. Hard drop — мгновенное падение до упора и 2 очка за ряд, фигура закрепляется сразу.

На уровне 15 интервал гравитации меньше шага симуляции, поэтому `advance` обязана за один вызов проходить несколько рядов, а не один.

#### T-spin

Условия, проверяемые в момент закрепления T-фигуры:

- последним успешным перемещением был поворот; успешный сдвиг влево или вправо флаг снимает, hard и soft drop — не трогают;
- из четырёх диагональных клеток вокруг центра T заняты три или больше; занятость за пределами поля считается занятой.

Если обе «передние» диагонали — те, куда смотрит ножка T в текущем состоянии поворота, — заняты, это полный T-spin. Если передняя только одна, это T-spin mini, который повышается до полного, когда сработала пятая проба wall kick.

Сверху добавляются:

- combo — `50 * combo * level`. Счётчик combo стартует с −1, увеличивается на единицу при каждом закреплении с очисткой и возвращается в −1 при закреплении без очистки. Первое очищение подряд даёт combo = 0 и бонуса не приносит, второе — combo = 1 и `50 * 1 * level`;
- back-to-back — умножает на 1.5 базовые очки за само очищение рядов и только их. Сложное очищение — Tetris или любой T-spin, очистивший хотя бы ряд, включая mini. Флаг ставится сложным очищением и снимается простым (single, double, triple без T-spin); закрепление без очистки на флаг не влияет.

Perfect clear — поле полностью пусто после очистки рядов. Бонус берётся из таблицы как есть и начисляется поверх очков за само очищение; множитель back-to-back на него не действует. Строка «Perfect clear tetris при back-to-back = 3200» — самостоятельное значение таблицы, а не `2000 * 1.5`.

Очищение T-spin'ом, оставившее поле пустым, своей строки в Guideline не имеет: начисляется база за T-spin с учётом back-to-back и сверху бонус perfect clear по числу очищенных рядов.

Soft drop даёт 1 очко за ряд, hard drop — 2, оба вне зависимости от уровня.

### Рендер

Два буфера кадра фиксированной ёмкости: текущий и предыдущий. Ёмкость — константа компиляции, 160 колонок на 60 рядов, то есть 9600 ячеек. Ячейка — codepoint и индекс цвета xterm-256, 8 байт; два буфера — около 153 КБ в статической памяти. Реальный размер терминала проверяется против ёмкости при старте; не влезает — игра не стартует с внятным сообщением.

Кадр строится целиком в памяти: рамки, панель, поле, активная фигура, ghost, наложения паузы и game over. Затем буферы сравниваются, и в терминал уходят только изменившиеся ячейки, объединённые в прогоны по строке. Курсор ставится абсолютно (`ESC[ряд;столбецH`), цвет — `ESC[38;5;Nm`, сброс — `ESC[0m`.

Все эскейпы кадра собираются в один байтовый буфер фиксированной ёмкости 32 КБ; когда он заполняется, он сбрасывается одним `write(STDOUT_FILENO, ...)`. Штатный кадр — один системный вызов, полная перерисовка — несколько. Никакого `fwrite` и `stdout` в потоке кадра: буферизация stdio смешалась бы с прямым `write`.

При входе: `ESC[?1049h` (alternate screen), `ESC[?25l` (скрыть курсор), полная перерисовка. При выходе: `ESC[0m`, `ESC[?25h`, `ESC[?1049l`.

### Ввод

`stdin` переводится в raw-режим через `tcgetattr` / `cfmakeraw` / `tcsetattr`, исходные настройки сохраняются. Готовность ввода выясняется через `poll()` на `STDIN_FILENO` с таймаутом, равным времени до границы кадра; флаги `fcntl` не меняются, так что шеллу не достаётся неблокирующий stdin. `poll`, вернувший готовность, означает, что `read` прочтёт хотя бы байт; вернувший 0 — что нажатий не было и кадр пора рисовать.

Каждую итерацию цикла вычитывается всё доступное, байты разбираются в очередь событий фиксированной ёмкости 64. Распознаются: `ESC [ A/B/C/D` — стрелки, `ESC O A/B/C/D` — стрелки в режиме application cursor, байт `0x20` — пробел, печатные `z`, `Z`, `c`, `C`, `p`, `P`, `q`, `Q`, `r`, `R`, байт `0x03` — Ctrl-C. Всё остальное отбрасывается.

Незавершённая эскейп-последовательность на конце прочитанного куска не обрабатывается как голый `ESC`, а переносится в начало следующего чтения; если накопленные байты уже не могут стать началом распознаваемой последовательности, они отбрасываются. В raw-режиме `ESC` сам по себе ни на что не назначен, поэтому таймер для различения голого `ESC` и CSI не нужен.

Привязки:

| Клавиша | Действие |
| --- | --- |
| ← / → | сдвиг на клетку, при удержании — DAS и ARR |
| ↑ | поворот по часовой |
| Z | поворот против часовой |
| ↓ | soft drop, пока удерживается |
| Пробел | hard drop |
| C | hold |
| P | пауза и снятие с паузы |
| R | новая партия на экране game over |
| Q или Ctrl-C | выход |

DAS — 100 мс, ARR — 0. По нажатию ← или → фигура сразу сдвигается на одну клетку, направление запоминается и запускается таймер DAS; по его истечении фигура одним шагом уезжает до стены, и повтор этого направления на этом заканчивается — при ARR = 0 ехать дальше некуда. Нажатие противоположного направления перехватывает повтор и запускает свой DAS заново. Отпускания терминал не сообщает, но здесь оно и не нужно: после сдвига до стены повтор ничего не меняет, а каждый следующий байт от автоповтора терминала просто заново сдвигает фигуру на одну клетку.

Soft drop устроен иначе, потому что «держу ↓» и «нажал ↓ один раз» терминал различить не даёт. Каждый байт ↓ опускает фигуру на один ряд, но не чаще одного раза за `softDropInterval`. Одиночное нажатие даёт ровно один ряд; удержание, которое терминал повторяет сам с частотой около 30 Гц, даёт скорость Guideline — интервал гравитации, делённый на 20. Приложение не ждёт отпускания и не ведёт собственного автоповтора стрелки вниз.

Оговорка к правилам: если автоповтор терминала выключен или медленнее `softDropInterval`, soft drop идёт со скоростью терминала, а не со скоростью Guideline. Это ограничение среды, а не логики.

Состояние DAS и задержки soft drop живёт в платформенном слое, не в `tetris::GameState`: логика получает уже готовые вызовы `tryShift` и `softDrop` и ничего не знает о том, что клавиша удержана.

### Время и цикл

Время — `clock_gettime(CLOCK_MONOTONIC)`; наносекунды приводятся к микросекундам, и весь учёт дальше идёт в них.

Симуляция — фиксированный шаг 1/120 с, то есть 8333 мкс, с аккумулятором в микросекундах. Остаток от деления не теряется, поэтому симуляция не отстаёт от реального времени. Реальная дельта кадра обрезается сверху 250 мс, число шагов за кадр — восемью, иначе подвисание терминала превращается в лавинообразный догон.

Цикл:

1. `poll` на stdin с таймаутом, равным времени до границы кадра; если готов — `read` и разбор в события.
2. Обработать события — каждое превращается в вызов чистой логики.
3. Взять текущее время, накопить дельту, отработать целое число шагов по 8333 мкс, передав в `tetris::advance` столько же на шаг.
4. Построить кадр в буфере, вывести дифференциально.

Отдельного `nanosleep` нет: ожидание до следующего кадра делает сам `poll` на шаге 1. Если кадр рисовался дольше бюджета, таймаут получается нулевым и цикл идёт без ожидания.

Игра завершается по `Q` или Ctrl-C.

### Терминал и его восстановление

Инициализация терминала — RAII-объект, чей деструктор восстанавливает `termios`, выходит из alternate screen и показывает курсор. Деструктор обязан сработать и при штатном выходе, и при возврате `false` из-за слишком маленького терминала. Флаги `fcntl` не меняются вовсе, поэтому восстанавливать их не нужно.

Провал проверки `assert_message` без зарегистрированного обработчика даёт `Action::Break`, то есть `TOYGINE_DEBUG_BREAK()` и смерть процесса без деструкторов: терминал остался бы в raw-режиме и alternate screen. Поэтому семпл вызывает `toy::assertion::initialize()` в начале `runInternal` и регистрирует через `setCallbacks` обработчик, который восстанавливает терминал, печатает полученную строку провала в stderr и возвращает `Action::Break`. `toy::assertion::deInitialize()` — на выходе.

Это осознанная граница: обработчик покрывает нарушение инварианта в отладочной сборке, где `TOYGINE_DEBUG` определён. Настоящий `SIGSEGV` терминал всё равно сломает, а в сборках без `TOYGINE_DEBUG` проверки не выполняются вовсе. Обработчики сигналов падения не добавляются намеренно — см. **Не-цели**.

Сигналы `SIGINT`, `SIGTERM`, `SIGHUP` перехватываются через `sigaction`: обработчик восстанавливает терминал и повторно поднимает сигнал с действием по умолчанию, чтобы код возврата остался честным. Обработчик не печатает ничего — только восстановление, поэтому состояние терминала хранится в файловой переменной, а не в объекте.

`SIGWINCH` перечитывает размер через `ioctl(TIOCGWINSZ)`. Пока терминал меньше 48 × 24, вместо поля рисуется сообщение «терминал слишком мал», а `tetris::advance` не вызывается вовсе; `Phase` при этом не меняется, чтобы снятие с паузы не вернуло игру в нечитаемый экран. Как только размер снова достаточен, рисунок и партия продолжаются с того же места — время, проведённое в тесном терминале, в симуляции не засчитывается.

Проверка, что вывод вообще идёт в терминал — `isatty(STDOUT_FILENO)` и `isatty(STDIN_FILENO)`. Не в терминал — не стартуем и сообщаем об этом через `writeErrorLine`, до входа в alternate screen.

### Точка входа

```cpp
class TetrisSampleApp final : public toy::application::ConsoleApplication {
public:
  constexpr explicit TetrisSampleApp(const toy::application::Version & version) noexcept;

private:
  bool runInternal() noexcept override;
};

IMPLEMENT_CONSOLE_APP(TetrisSampleApp)
```

`runInternal` проверяет терминал, создаёт RAII-хранитель настроек, запускает цикл, возвращает результат. Вся диагностика — `writeErrorLine` до входа в alternate screen и после выхода из него; внутри alternate screen печатать в stdout мимо кадрового буфера нельзя.

`ConsoleApplication` даёт семплу точку входа, версию для экрана game over и поток диагностики. Сам вывод кадра идёт напрямую в `write(STDOUT_FILENO, ...)` — до появления в движке консольного видео API это единственная честная граница.

### Сборка

`samples/tetris/CMakeLists.txt`:

```cmake
add_executable(tetris-sample-app
  tetris_sample_app.cpp
  tetris_core.cpp
  terminal_screen.cpp
  terminal_input.cpp)

target_link_libraries(tetris-sample-app PRIVATE toygine toygine::compile::warnings)
set_target_properties(tetris-sample-app PROPERTIES FOLDER "samples")

# CMAKE_CXX_EXTENSIONS OFF даёт __STRICT_ANSI__, а glibc за ним прячет cfmakeraw, SIGWINCH и TIOCGWINSZ.
target_compile_definitions(tetris-sample-app PRIVATE _DEFAULT_SOURCE _GNU_SOURCE _DARWIN_C_SOURCE)

install(TARGETS tetris-sample-app RUNTIME DESTINATION bin COMPONENT samples)
```

Макросы объявляются только для таргета семпла и ни для чего больше: `PUBLIC` здесь был бы ошибкой, потому что утёк бы в потребителей `toygine`.

`samples/CMakeLists.txt` подключает каталог только там, где семпл вообще может собраться:

```cmake
if (TOYGINE_TARGET_PLATFORM STREQUAL "Linux Desktop" OR TOYGINE_TARGET_PLATFORM STREQUAL "macOS Desktop")
  add_subdirectory(tetris)
endif()
```

Опция `TOYGINE_BUILD_SAMPLES` уже существует и уже подключает `samples/` в корневом `CMakeLists.txt`, ничего нового не нужно.

## Что остаётся на усмотрение строящего

- Точные координаты каждой панели в клетках терминала — известны размеры и зазоры, расстановка внутри них очевидна.
- Точные индексы xterm-256 для цветов: таблица выше — отправная точка, её стоит подбирать, глядя на экран.
- Как именно кодируется UTF-8 глиф в буфере вывода — руками тремя байтами или через стандартную библиотеку.
- Раскладка наложения паузы и экрана game over поверх поля.
- Ёмкости очередей и буферов, если 64 события и 32 КБ вывода окажутся неудобны; менять смысл фиксированной ёмкости на динамическую нельзя.
- Внутреннее устройство `tetris_core.cpp`: какие вспомогательные функции столкновений, очистки рядов и начисления очков вынести, и стоит ли дробить файл на несколько переводов единицы, если он вырастет за пределы читаемого.
